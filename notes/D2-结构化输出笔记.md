## 0. 为什么这件事必须做（承接 D1 的结论）

D1 实测过：**`temperature=0` 加 `seed=42`，三次输出依然不同。**
所以"模型输出→程序消费"这条链路上，**任何依赖输出稳定性的假设都是错的**。

而 LLM 应用的绝大多数崩溃，都发生在这一层：

| 现象 | 根因 |
| --- | --- |
| 下游代码 `KeyError: 'order_no'` | 模型这次把字段写成了 `order_number` |
| `int("1250 pcs")` 抛异常 | 模型把数量写成了带单位的字符串，schema 要 integer |
| `json.loads` 抛 `JSONDecodeError` | 模型在 JSON 前后加了 ```json 代码块或"好的，以下是…" |
| 偶发但无法复现的线上故障 | 上面三种在高并发下随机命中，抽样测试测不出来 |

**核心命题**：不要"请求"模型给结构化数据，要**用协议约束**它，再用**校验层**兜底。

---

## 1. 四层防线（从弱到强）

```
第 0 层  靠 prompt 说「只输出 JSON」        ← 最弱，字段名和类型都不受控
第 1 层  response_format = json_object      ← 只保证"是合法 JSON"，不保证内容
第 2 层  response_format = json_schema      ← 字段名 + 类型都被约束（推荐）
第 3 层  tool calling                        ← 用函数签名当契约，适合要触发副作用的场景
────────────────────────────────────────────
所有层之上：Pydantic 校验 + 失败重试 + 降级   ← 必须有，因为前四层都不是 100%
```

**关键认知：没有任何一层能给你 100%。** 第 3 层也可能给出 schema 外的值、
也可能 JSON 解析失败。所以校验与重试不是可选项。

---

## 2. 四种方式在协议层到底做了什么

| 方式 | 服务端做了什么 | 模型侧约束 |
| --- | --- | --- |
| 纯 prompt | 什么都不做 | 无。全靠模型"听话" |
| `json_object` | 在解码时**屏蔽掉不能构成合法 JSON 的 token**，保证输出是合法 JSON 对象 | 仅保证语法合法，**字段名/类型完全自由** |
| `json_schema`（++strict） | 把 schema **编译成语法约束**，在解码阶段禁止违反 schema 的 token | 字段名、类型、必填、枚举都被强制 |
| tool calling | 把工具签名作为**可调用契约**注入 prompt，模型返回结构化调用请求 | 参数结构受 schema 约束，但要自己解析 `arguments` 字符串 |

**理解要点**：`json_object` 和 `json_schema` 的差别不是"提示词写得好不好"，
而是**在解码阶段（token 采样时）施加约束**。这是本质区别——
它不是"请求模型遵守"，而是"让模型在物理上无法违反"。

## 3. 【已实测】支持矩阵与行为差异

**测试任务**：从一段中文订单文本里抽取 `order_no / vendor / qty / total` 四个字段。
**测试方式**：每种方式各调一次，检查 `finish_reason`、输出 token、`json.loads` 是否成功、**实际键名**。

| # | 方式 | 结果 | 输出 token | 实际键名 |
| --- | --- | --- | --- | --- |
| 1 | 纯 prompt（"只输出 JSON"） | ✅ 合法 JSON | 95 | ❌ **`order_number` `supplier` `order_date` `quantity` `unit_price` `total_amount`** |
| 2 | `json_object`，prompt **不含** "json" 字样 | ❌ **400 报错** | — | — |
| 3 | `json_object`，prompt 含 "json" 字样 | ✅ 合法 JSON | 95 | ❌ **同样自己编字段名** |
| 4 | **`json_schema`（strict=true）** | ✅ | 63 | ✅ **完全按 schema**：`order_no` `vendor` `qty` `total` |
| 5 | tool calling（强制指定函数） | ✅（在 `tool_calls` 里） | 84 | ✅ 参数按 schema |

### 四个必须记住的发现

**① `json_object` 和"纯 prompt"在这些维度上几乎没差别。**
两者都只保证"是合法 JSON"，**字段名由模型自创**。
所以"我用了 `json_object` 所以稳了"是**错的**——它只挡住了语法错误，没挡住语义漂移。

**② `json_schema` 才是真正的结构化输出。**
输出 token 从 95 降到 63（少了自由发挥），字段名精确匹配，
而且**类型被强制**：`qty` 是 integer `1250`，不是字符串 `"1250 pcs"`。

> **这是本笔记最重要的一条**：如果你要把输出喂给数据库或下游函数，
> 只能用 `json_schema` 或 tool calling，不能用 `json_object`。

**③ `json_object` 有一个隐藏约束（很容易踩）**：

```
400 invalid_parameter_error:
'messages' must contain the word 'json' in some form,
to use 'response_format' of type 'json_object'
```

prompt 里**必须出现 "json" 这个词**（大小写不限、形式不限）。
这是 OpenAI 的老规矩，百炼照搬了。报错信息很清楚，遇到就补一下 prompt。

**④ tool calling 的两个陷阱（D3 会天天遇到）**：

- 走 tool calling 时 **`content` 是空字符串**，参数在 `tool_calls[*].arguments` 里；
- **`arguments` 是 JSON 字符串，不是 dict**：

```python
# 实测返回值
tool_calls = [
    {
        "id": "call_bef36cf0972142fe9441c790",
        "name": "save_invoice",
        "arguments": '{"order_no": "PO-2026-1012-0087", "vendor": "杭州云栖智能科技有限公司", "qty": 1250, "total": 48125}',
    }
]

args = json.loads(tool_calls[0]["arguments"])  # ← 必须先解析
```

**而且 `finish_reason` 不可靠**：强制 `tool_choice` 时会返回 `stop` 而不是 `tool_calls`。

| 场景 | `finish_reason` | `tool_calls` 数 |
| --- | --- | --- |
| 传 tools，不强制 | `tool_calls` | 1 |
| tools + `tool_choice="auto"` | `tool_calls` | 1 |
| **tools + 强制指定函数** | **`stop`** | **1** ⚠️ |
| 不传 tools | `stop` | 0 |

→ **判据必须是 `len(tool_calls) > 0`**，不能只看 `finish_reason`。

## 4. 【已实测】`json_schema` 的正确写法

```python
SCHEMA = {
    "name": "Invoice",
    "strict": True,
    "schema": {
        "type": "object",
        "properties": {
            "order_no": {"type": "string"},
            "vendor": {"type": "string"},
            "qty": {"type": "integer"},
            "total": {"type": "number"},
        },
        "required": ["order_no", "vendor", "qty", "total"],  # strict 模式下必须全列
        "additionalProperties": False,  # strict 模式要求
    },
}

r = client.chat(
    [{"role": "user", "content": f"抽取订单信息。文本：{SRC}"}],
    temperature=0.0,
    reasoning_effort="none",  # ← D1 的结论：抽取类任务不需要思维链
    response_format={"type": "json_schema", "json_schema": SCHEMA},
)
data = json.loads(r.text)
```

**strict 模式的三个要求**（OpenAI 规范，百炼兼容）：
1. `strict: True` 必须显式给出；
2. **所有** property 都要列进 `required`（不支持"可选字段"）；
3. 必须 `additionalProperties: False`。

如果需要表达"字段可能读不到"，做法是 **类型里允许 null**，而不是从 `required` 里去掉：

```python
{"order_no": {"type": ["string", "null"]}}  # ✅ 保留在 required，但允许 null
```

## 5. 工程落地：校验 + 重试 + 降级

**四层防线之上必须有这一层。** 参考实现：

```python
from pydantic import BaseModel, Field, ValidationError


class Invoice(BaseModel):
    order_no: str = Field(min_length=1)
    vendor: str = Field(min_length=1)
    qty: int = Field(gt=0)  # ← 业务约束也放进来
    total: float = Field(gt=0)


def extract_invoice(text: str, *, max_retry: int = 2) -> Invoice | None:
    """结构化抽取：schema 约束 → Pydantic 校验 → 失败重试（带错误反馈）→ 降级返回 None。"""
    messages = [{"role": "user", "content": f"抽取订单信息。文本：{text}"}]

    for attempt in range(max_retry + 1):
        r = client.chat(
            messages,
            temperature=0.0,
            reasoning_effort="none",
            response_format={"type": "json_schema", "json_schema": INVOICE_SCHEMA},
        )
        try:
            return Invoice.model_validate_json(r.text)
        except ValidationError as exc:
            if attempt == max_retry:
                # 降级：不抛异常，返回 None 并留痕。
                # 生产环境这里必须记 trace + 进 Bad Case 池（D18）。
                logger.warning("抽取失败 run=%s err=%s", r.model, exc.errors()[:2])
                return None
            # ⭐ 关键：把校验错误回传给模型再试一次，而不是原样重发
            messages.append({"role": "assistant", "content": r.text})
            messages.append(
                {
                    "role": "user",
                    "content": f"校验失败：{exc}. 请修正后重新输出，不要解释。",
                }
            )
    return None
```

**四个设计要点**：

| 要点 | 原因 |
| --- | --- |
| 用 `model_validate_json` 而不是先 `json.loads` 再 `model_validate` | 少一次中间态，错误信息更聚焦 |
| 重试时**把校验错误回传** | 原样重发在 `temperature=0` 下大概率得到同样结果，实测过不可复现性问题 |
| 失败**降级返回 None 而不是抛异常** | 单条失败不应中断整个批处理；但要记 trace |
| 业务约束（`gt=0`、`min_length=1`）放进 Pydantic | 让"模型输出错"和"业务数据非法"用同一套机制拦下来 |

## 6. 【待你实测】跑批对比实验（D2 的核心作业）

**为什么必须自己跑**：第 3 节我只跑了各一次。真实的成功率差异需要 N≥30 次才能看出来，
而这个"跑批 + 统计成功率"的动作**就是 D16 评测体系的雏形**。

### 实验设计

| 项 | 设置 |
| --- | --- |
| 样本 | 30 条文本（建议：10 条干净、10 条含噪声/单位混杂、10 条边界：字段缺失/超长/多语言） |
| 对照组 | ① 纯 prompt ② `json_object` ③ `json_schema` ④ tool calling |
| 每组次数 | 30（每个样本各跑一次；想更稳可以对同一样本跑 3 次取多数） |
| 固定参数 | `temperature=0`、`reasoning_effort="none"`、`max_tokens=400` |
| 总调用数 | 4 组 × 30 = **120 次**（用 `max_tokens=400` 控制成本） |

### 必须记录的七个字段（每个样本一行）

| 字段 | 说明 |
| --- | --- |
| 方式 | ①②③④ |
| 样本 ID | 可回溯 |
| `json.loads` 是否成功 | 语法层 |
| 字段名是否完全匹配 | 语义层——**这是 `json_object` 会输的地方** |
| 类型是否匹配 | 语义层——`qty` 是 int 还是 str |
| Pydantic 校验是否通过 | 业务层 |
| 输出 token / 延迟 ms | 成本层 |
| `finish_reason` | 有没有被截断 |

### 结果表格（跑完填这张）

| 方式 | JSON 可解析率 | 字段名匹配率 | 类型匹配率 | Pydantic 通过率 | 平均输出 token | P50 延迟 |
| --- | --- | --- | --- | --- | --- | --- |
| ① 纯 prompt | | | | | | |
| ② `json_object` | | | | | | |
| ③ `json_schema` | | | | | | |
| ④ tool calling | | | | | | |

### 验收标准（达到才算 D2 完成）

- [ ] 表里每个格子都有数字，没有"目测还行"
- [ ] 能解释 ② 与 ③ 在"字段名匹配率"上的差距（预期 ② 明显低于 ③）
- [ ] `json_schema` 的 **Pydantic 通过率 ≥ 95%**（达不到就说明 schema 设计或重试策略有问题）
- [ ] 对失败样本做了**错误分类**（语法错 / 字段名漂移 / 类型错 / 截断），每类有占比
- [ ] 实验脚本入库，能一键重跑（因为 prompt 一改就要重测——这是回归套件的起点）

### 错误分类模板（这一步比成功率更重要）

```
语法错误（JSON 不可解析）        :  N 条，占 X%
字段名漂移（键名不在 schema 里）  :  N 条，占 X%
类型错误（string vs int）        :  N 条，占 X%
截断（finish_reason=length）     :  N 条，占 X%
业务校验失败（qty<=0 等）        :  N 条，占 X%
```

> **为什么强调错误分类**：只报一个"成功率 87%"没法优化；
> 知道"其中 60% 是字段名漂移"才能决定是换 `json_schema` 还是改 prompt。
> 这个思路直接对应 JD 里那句「Bad Case 平台 / 错误分类 / 基线」。

## 7. 面试话术

**「你怎么保证模型输出能被程序消费？」**
> 分四层。prompt 层面我会说清楚字段，但那只是最弱的一层。
> 真正起作用的是协议层：`json_schema` 加 strict 是在**解码阶段**屏蔽掉违反 schema 的 token，
> 属于物理约束，不是请求模型配合。
> 我实测过差异：纯 prompt 和 `json_object` 都会让模型**自创字段名**
> （我要 `order_no`，它给了 `order_number`），而且把 quantity 写成字符串 `"1250 pcs"`；
> 换成 `json_schema` 之后字段名和类型都精确匹配，输出 token 还少了三分之一。
> 最后一定有校验收尾：Pydantic 校验，失败时**把校验错误回传给模型重试**，
> 再失败就降级返回并进 Bad Case 池。

**「为什么不能只靠 `json_object`？」**
> 因为它只保证"是合法 JSON"，不保证"是你要的 JSON"。
> 我实测过：prompt 说"只输出 JSON"和用 `json_object`，产出的字段名一模一样，都是模型自己编的。
> 所以只要下游要按字段名取值，就必须用 `json_schema` 或 tool calling。

**「tool calling 有什么坑？」**
> 两个。第一，参数在 `tool_calls[*].arguments` 里且**是 JSON 字符串不是 dict**，
> 不解析直接用会 TypeError；走 tool calling 时 `content` 是空字符串，
> 如果你只读 `content` 会以为模型没说话。
> 第二，**不能用 `finish_reason == "tool_calls"` 判断是否需要调工具**——
> 实测强制 `tool_choice` 时它返回的是 `stop`。判据必须是 `tool_calls` 非空。

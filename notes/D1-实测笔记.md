# D1 实测笔记 —— LLM 应用工程的 10 条一手结论

> 生成日期：2026-10-12
> 环境：Python 3.12 / openai SDK 3.29 / 阿里云百炼 DashScope OpenAI 兼容接口
> 主力模型：`qwen3.8-flash`（推理模型）／视觉：`qwen3.8-max`
> 用途：① D17 成本与延迟优化的依据；② W7 面试「你怎么理解 LLM 应用工程」的原始素材
>
> **所有数字都是我自己跑出来的，不是文档抄的。** 每条都写了验证方式，面试官追问"你怎么知道的"时可复述。

## 0. 为什么这十条值得记

合并约 50 条真实 JD 后，"可观测与评测"命中率 37-67%，横跨四种完全不同的岗位类型
（影石／拼多多／联想／昆仑万维），是**唯一被所有类型都要求的工程能力**。

而这十条结论全都是"不看指标就一定会误判"的例子。它们构成的能力，
就是 JD 里反复出现的那句话：**能报出成功率、延迟、Token 消耗，并且知道这些数字怎么来的。**

## 1. 推理模型的思维链占输出成本的三分之一以上

**验证方式**：同一 prompt 跑流式与非流式，对比 `usage.completion_tokens` 与 `visible_tokens`。

| 请求 | 输出 token | 其中思维链 | 可见正文 | 思维链占比 |
| --- | --- | --- | --- | --- |
| 「数 1 到 3，只输出数字」 | 78 | 3 字符内容 | 3 字符 | 96% 的分片是思维链 |
| 「解释 HashMap 底层结构」 | 692 | 256 | 436 | **37%** |
| 「一句话说明 CAP 定理」 | 79 | 41 | 38 | 52% |
| 「数 1 到 3」原始分片 | 78 | 59/64 个分片 | 2 个分片 | — |

**关键事实**：
- 思维链放在 `delta.reasoning_content`，**不在** `delta.content` 里；
- 它**按输出 token 计费**（和正文同价）；
- 不单独统计它，成本优化就永远找不到大头。

**工程做法**：`Usage` 里加 `reasoning_tokens`，并派生 `visible_tokens = completion - reasoning`。
`PRICES_CNY_PER_1K` 按 `resp.model` 返回的模型名做 key（不是 `.env` 里的变量值）。

## 2. ⚠️ `max_tokens` 管不住思维链（推翻了一个常见假设）

**验证方式**：固定 prompt，扫描 `max_tokens ∈ {4, 16, 64, 256}`。

| max_tokens | finish_reason | 总输出 | **思维链** | 可见正文 |
| --- | --- | --- | --- | --- |
| 4 | length | 355 | **347** | 8 |
| 16 | length | 209 | **191** | 18 |
| 64 | length | 356 | **290** | 66 |
| 256 | length | 771 | **513** | 258 |

**两个结论**：
1. **`visible` 大体跟着 `max_tokens` 走**（≈ max_tokens + 少量溢出），
   **但 `reasoning` 完全不受约束**——`max_tokens=4` 时照样烧 347 个思维链 token。
2. 四个档位**全部是 `length`**，所以对推理模型而言 `finish_reason == "length"` 的
   **区分度下降**，不能简单用它判断"输出被截断了"。

**所以**：「设了 `max_tokens` 就有输出预算护栏」这句话对推理模型是**错的**。
成本护栏的第一道防线必须是**是否开启思维链**，而不是 `max_tokens`。

---

## 3. 关掉思维链的正确开关，以及一个反直觉结果

**验证方式**：同一 prompt 试 6 种参数写法。

| 写法 | 输出 token | 思维链 | 是否可用 |
| --- | --- | --- | --- |
| 不传任何参数（基线） | 79 | 41 | — |
| **`reasoning_effort="none"`** | **39** | **0** | ✅ **省 51%** |
| **`extra_body={"enable_thinking": False}`** | 41 | 0 | ✅ 有效 |
| `reasoning_effort="low"` | 95 | 53 | ⚠️ **比基线更贵** |
| `enable_thinking=False`（直接传） | — | — | ❌ SDK 拒绝：unexpected keyword |
| `thinking={"type": "disabled"}` | — | — | ❌ SDK 拒绝 |

**要点**：
1. 两级参数（`reasoning_effort` / `extra_body.enable_thinking`）都能关，但**直接传会被 SDK 拦掉**，
   必须放进 `extra_body`。
2. **`"low"` 比不传还贵**——参数语义不能想当然，必须实测。
3. **决策规则**：需要推理的任务（多步规划、代码、数学）保留思维链；
   抽取／分类／改写／格式化这类任务关掉。**这是 D17 成本优化的第一把刀。**

## 4. 每个请求有约 60 个 token 的固定开销

**验证方式**：长度扫描——发不同长度的输入，看 `prompt_tokens` 的下界。

| 输入 | prompt tokens |
| --- | --- |
| 空字符串 | **61** |
| 10 个 `A` | 63 |
| 100 个 `A` | 74 |
| 1000 个 `A` | 186 |

**结论**：发一个「好」字也要付约 60 token。

**工程含义**：
- 固定开销随**调用次数**增长，不随 token 量增长
  → **减少调用次数比缩短 prompt 更有效**
- 做成本估算时先加 60 再算内容，否则对短请求会低估一个数量级
- 这条支撑 D3 的设计决策：**能不能把 3 次小调用合并成 1 次，是成本问题不是代码风格问题**

---

## 5. TTFT 必须分段定义，否则指标会骗人

**验证方式**：流式逐分片打时间戳，区分"任何分片"与"首个正文分片"。

实测一次「解释 HashMap 底层结构」：

| 阶段 | 耗时 | 用户看到什么 |
| --- | --- | --- |
| 排队 + prefill + 网络 | 3634 ms | 空白 |
| **思维链阶段** | **6170 ms** | **仍然空白**（占 61%） |
| TTFT（正文首字） | **9804 ms** | 第一个字 |
| 正文生成 | 7238 ms | 正文 |
| 总耗时 | 17042 ms | — |

**结论**：
- 若把 TTFT 定义成"第一个分片"（3634ms）vs"第一段正文"（9804ms），
  两个数字差 6.2 秒，**对应的用户体验完全不同**。
- **产品含义**：如果不展示思维链，用户要干等 6 秒以上什么都不显示
  → 这正是 ChatGPT / Claude / DeepSeek 都展示"思考中"的原因。
- 多次采样还发现：TTFT 在 3.2s ~ 6.1s 之间波动（近 2 倍），
  **只看单次测量会得出完全错误的结论**，必须看 P50/P95。

## 6. `temperature=0` + `seed` 也不可复现

**验证方式**：同 prompt × 3 次，分别在 `T=0.01`、`T=1.2`、带 `seed=42` 三种设置下对比。

| 设置 | 三次结果 |
| --- | --- |
| `T=0.01, seed=42` | ❌ 3 种不同输出 |
| `T=1.2, seed=42` | ❌ 2 种不同输出 |
| `T=0.01, 无 seed` | ❌ 3 种不同输出 |

**这条的三个直接后果**（也是 D15-D17 评测模块存在的理由）：
1. 任何"输出必须逐字相等"的测试（exact match）**都会 flaky**，不能作为验收标准；
2. 对比"改了 prompt / 换了模型有没有退化"**必须多次采样 + 统计**，单次对比毫无意义；
3. 测试与评测必须走**语义判定**（Schema 校验 + 关键要素覆盖 + LLM-as-Judge），而不是字符串比对。

**另一个观察**：`T=1.2` 时出现语病「系统设计**地**组织」——
高温不只是"更多样"，它**会引入错误**。

## 7. 流式协议的三个字段分布（含一个必须记住的指纹）

**验证方式**：把原始分片逐条打印出来。

一个推理模型的完整流（64 个分片）：

```
序号        字段                          含义
────────────────────────────────────────────────────────────────────
  0..58     delta.reasoning_content      思维链（按输出价计费）
 59..60     delta.content                '1' ' 2 3'   ← 用户可见内容
 61         delta='' finish_reason=stop   ← 状态片：delta 为空
 62         choices=[] usage={...}        ← 总账片：choices 为空数组
────────────────────────────────────────────────────────────────────
```

**要点**：
1. **`usage` 只能在最后一个分片拿到**，因为 `completion_tokens` 在生成结束前**不存在**。
   它的指纹是 **`choices` 为空数组** `[]`——表示"这是整个请求的总账，不属于任何一次生成"。
2. `finish_reason` 表达的是**流的状态**，不是内容，所以它所在的片 `delta` 通常为空。
   但要认识全部取值：`stop` / `length` / `tool_calls` / `content_filter`。
3. ⚠️ **不要依赖分片顺序**。不同 provider 切法不同（有的把 `finish_reason`
   和最后一段内容放同一片）。健壮写法是**每个分片都同时检查四个字段**
   （`reasoning` / `delta` / `usage` / `finish_reason`）。
4. **`stream_options={"include_usage": True}` 是 opt-in**（多发一个分片有开销），
   且不是所有 provider 都支持——不支持时会报错，需要能关掉它。

**工程推论（这条改写 D18 的设计）**：
> 你**无法在流式过程中知道已经花了多少 token**
> → 预算护栏**不能**设计成"流到一半发现超预算就叫停"
> → 只能 **事前约束**（`reasoning_effort` / 步数上限 / 工具次数上限 / 上下文上限）
>   + **事后记账**（从末分片读 usage）+ 离线估算器做中途粗算。

## 8. ⚠️ `finish_reason == "tool_calls"` 不能单独作为"模型要调工具"的判据

**验证方式**：四种工具配置各跑一次，对比 `finish_reason` 与 `tool_calls` 是否一致。

| 场景 | `finish_reason` | `tool_calls` 数 | 一致？ |
| --- | --- | --- | --- |
| 传 tools，不强制 `tool_choice` | `tool_calls` | 1 | ✅ |
| 传 tools + `tool_choice="auto"` | `tool_calls` | 1 | ✅ |
| **传 tools + 强制指定函数** | **`stop`** | 1 | ⚠️ **不一致** |
| 不传 tools（模型无法调用） | `stop` | 0 | ✅ |

**正确判据**：`len(tool_calls) > 0`。`finish_reason` 只能作辅助信号。

**D3 的 Agent 循环必须这样写**：

```python
while True:
    resp = call_model(messages)
    if not resp.tool_calls:  # ← 判据是 tool_calls 非空，不是 finish_reason
        break
    messages.append(resp.message)  # assistant 的 tool_calls 要追加回去
    for call in resp.tool_calls:
        args = json.loads(call["arguments"])  # ⚠️ arguments 是字符串
        messages.append(execute(call["name"], call["id"], args))
```

**两个额外的坑**：
- 走 tool calling 时 **`content` 是空字符串**，参数全在 `tool_calls[*].arguments` 里；
- `arguments` 是 **JSON 字符串**，不是 dict。直接当 dict 用会 `TypeError`。
  也**不要提前吞掉解析异常**——解析失败本身是需要上层处理的结果。

## 9. 模型名要实测，不要按命名习惯推断

**验证方式**：6 个候选名各发一次带图请求。

| 模型名 | 结果 |
| --- | --- |
| **`qwen3.8-max`** | ✅ **能读图**，正确读出订单号 |
| **`qwen3-vl-plus`** | ✅ 能读图（526 tok，略省） |
| `qwen-vl-max` / `qwen-vl-plus` / `qwen3-vl-max` / `qwen3.8-vl-max` | ❌ 全部 404 Model not exist |

**教训**：我一开始按"带 `vl` 才支持视觉"的命名习惯判断 `qwen3.8-max` 不能读图——
**判断错了**。文档、习惯、别人的经验都不能替代一次真实调用。

**顺带一个成本数据**：一张 900×560 的图 ≈ **537 输入 token**。
100 页文档若全走视觉模型 ≈ 53,700 token → 所以 D4 的摄取策略必须分流：
**文字版 PDF / HTML / Markdown 直接抽文本（几乎免费），只有扫描件才走视觉模型。**

## 10. 指令是否生效，必须用"可检测"的方式验证

**验证方式**：给 Agent 一条可留下痕迹的指令，连跑 3 次看痕迹在不在。

背景：我第一次给 Agents SDK 写的 `instructions` 是
`"A helpful assistant, only answer in English."`，
但用中文提问「你是谁？」，回答**也是中文**。

于是有歧义：是 `instructions` 没传进去，还是模型没遵守？
用一条可检测的指令就能区分：

| instructions | 提问 | 三次输出 | 是否遵守 |
| --- | --- | --- | --- |
| `only answer in English` | 你是谁？ | 中文 | ❌ |
| `每条回答必须以 [EN] 开头，且只用英文` | 你是谁？ | 3/3 都以 `[EN]` 开头且全英文 | ✅ |

**两个结论**：

1. **`instructions` 确实作为 system prompt 传进去了**（3/3 遵守），框架没问题。
2. **模糊约束会被忽略**：`only answer in English` 是软约束，模型看到用户用中文，
   就自行判断"用中文更自然"。换成**具体且可检测**的约束（必须有某个前缀）后立刻生效。

**工程做法（这条直接用于 D2 和 prompt 版本管理）**：
- 写 prompt 时，**每条关键约束都要能翻译成"可判定的检查"**。
  写不出检查的，就是还没想清楚——这正是 `Vibe Coding 工程化实践.md` 里
  "每条需求都要能写出验收标准"的同一个道理。
- 验证指令是否生效，**不要靠肉眼看一次输出**。要看可检测的痕迹，或者跑批统计遵守率。
- 这条对应 JD 里的「扎实的 Prompt 编写与调优能力」和「错误分类 / 基线」——
  **调 prompt 的前提是能测量它**。

## 11. 这一天的元结论（比十条数据更值钱）

今天出现了**四次"我的判断被实验推翻"**，方向各不相同：

| 我的判断 | 实验结果 |
| --- | --- |
| `qwen3.8-max` 是文本模型，不能读图 | ❌ 错，能读图 |

这条经验本身可以写进简历和面试：**"我的技术判断都带验证步骤，不靠记忆和推断。"**

## 12. 面试话术（把这些数据讲成答案）

**「你怎么控制 LLM 应用的成本？」**
> 分层来看。先看**要不要花**：推理模型有思维链，实测占输出 token 的 37%，
> 抽取类任务用 `reasoning_effort="none"` 关掉能省一半。
> 再看**固定开销**：实测每个请求有约 60 token 的固定成本，所以减少调用次数比缩短 prompt 更有效。
> 最后看**上下文**：Agent 多步任务每步都带全文档的话，输入成本线性增长，要做上下文压缩。
> 而且 `max_tokens` 管不住思维链——这个我实测过，所以护栏只能做在"事前配额"上。

**「你怎么优化首字延迟？」**
> 先分段量。实测一次请求里，思维链阶段占 61% 的时间而用户什么都看不到，
> 首字延迟是 9.8 秒，总耗时 17 秒。
> 所以要么展示思考过程，要么关掉思维链，要么换非推理模型。
> 另外 TTFT 本身波动接近 2 倍（3.2~6.1s），所以必须看 P95 而不是单次测量。

**「你怎么保证改了 prompt 没退化？」**
> 不能靠单次对比。实测 `temperature=0` 加 `seed=42`，三次输出依然不同——
> 所以字符串比对一定会 flaky。必须建 Golden Set 做多次采样的 pass rate，
> 判定用 Schema 校验加 LLM-as-Judge，而不是精确匹配。
